## Agent


You have the three options roughly right; here they are stated more precisely, then my recommendation.

## The three designs

**A. Today's behaviour: apply per item, verify after writing.**
- Each row in the report is applied on its own. A rejected or unanswered decision never blocks unrelated rows; that is principle P7 in the sync design note.
- All mutations are written to disk first (atomically, ≤4 files). Only then does the structural verify check that the DE and EN halves still line up.
- Since #992 the verify gate is scoped per slide group, but it only withholds the ledger **recording** for a failing group. The bad bytes stay on disk.

So your first bullet is close, but it misses the part that hurts: the pairs left "open for correction" can be structurally broken on disk. In #1051 a cell was actually lost.

**B. Verify the projected files before writing.**
`apply_deck` already holds the final file contents in memory before it writes. It already runs one pre-write gate, a re-parse that writes nothing if it fails. The structural verify could run over those in-memory files instead of the files on disk. It comes in two strengths:
- **B1, deck-wide:** any violation means nothing is written.
- **B2, scoped:** drop the mutations for the slide groups the verify flags, verify again, and write the rest. This is #992's scoping, applied to the write itself rather than only to the recording.

**C. Hold back dependent rows before anything runs.**
This is a static rule, not a reaction to a verify failure. A mechanical row is held back when the same cell also carries a question that was rejected or left unanswered in this pass. In #1051 that means the `mirror_remove` would wait because its `verify_cold` sibling was rejected. It follows the same "defer, re-derive next pass" pattern as the #824 and #885 fixes.

## What matters for agents

1. **What's on disk is always valid.** An agent should never need `git restore`, which is the only workaround #1051 offers and which also throws away the good work. There is a second danger: the design note's #885 entry describes how a written-but-unrecorded state gets read back on the next pass as if an author had made that edit. A broken intermediate file doesn't just sit there; it gets laundered into the next sync pass's input.
2. **Progress isn't held hostage.** One bad answer, or one engine bug in one slide, must not block the rest of the deck. #992 was exactly that failure: agents re-answering 11+ confirms per deck.
3. **One simple contract.** Agents do best with "after apply, the files always verify; everything not done is listed in `left_undone` with a reason; re-run report and answer what remains." Since the handles stay stable across passes, re-submitting answers is cheap for an agent.

## Recommendation: B2 as the guarantee, C as a refinement

- **A** fails point 1. Writing bytes you already know fail the verify helps nobody: the engine refuses to record them, and an agent can't easily undo them.
- **B1** satisfies 1 and 3 but fails 2. One persistent engine bug in one slide group would freeze the whole deck until a human steps in. That is #992 again, just applied to the write instead of the save.
- **B2** satisfies all three. It is the only option that guarantees "never write a broken deck" for failure modes nobody has anticipated yet. This latest batch of bugs shows the differ will keep producing a few of those (#1051, #1052, #1054, #1071).
- **C** alone fixes only the dependency pattern from #1051. On top of B2 it still earns its place: without it, B2 would hold back the whole slide group, including the good `code/2` placement answer. With it, only the dependent row waits and the rest of the group lands.

B2 doesn't actually reverse the per-item doctrine, despite the comment on #1051 saying so. P7 promises that unrelated items aren't blocked and completed work isn't lost. A mutation that fails the verify isn't completed work. B2 keeps everything P7 actually promises and changes one sentence of #992's rationale, "landed mutations stay," which matters for #885.

**Cost:**
- B2: the verify gate has to take the in-memory files instead of reading from disk, and there's a withhold-and-reverify loop (at most a few iterations, since each round drops at least one group).
- C: a pre-execution check of the kind #824 and #885 already use.
- Both need an amendment row in the design note.
