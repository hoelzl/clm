I've investigated #1309 and its diagnosis is correct; I checked each part against the code. I haven't changed any code. My recommendation is the issue's option (a), applied when each notebook's kernel is launched, plus a better-worded warning.

## Root cause

1. **The proxy settings reach every process in the build.** `_maybe_start_mitmproxy_transport` (`src/clm/build/engine.py:311`) writes the proxy variables (`HTTP(S)_PROXY`/`http(s)_proxy`), the three certificate variables and `PIP_DISABLE_PIP_VERSION_CHECK` into the host's `os.environ`. It also overwrites any proxy the user had set before the build, such as a corporate one.
2. **Each kernel copies that environment.** `TrackingExecutePreprocessor` starts kernels without passing an `env`, so jupyter_client falls back to `os.environ.copy()` (`provisioner_base.py:156`). Docker mode behaves the same way: the container gets the proxy variables (`worker_executor.py:150`) and its kernels inherit them.
3. **Only opted-in topics get tagged.** `_resolve_mitmproxy_tag` (`notebook_processor.py:2090`) returns `None` for a topic without `http-replay`, so no tag code is injected. That deck's `requests` traffic reaches the proxy untagged.
4. **The proxy then mishandles that traffic** (`addon.py:450-475`). In recording modes it records it into the machine-local catch-all cassette. In strict modes (`replay`, or `once` with an existing cassette) it refuses the request with a 404. I haven't run that strict case, but nothing in the code path stops it: a deck that never opted in fails on its first network call. `replay` is the default when `CI=true`.

## Proposed fix

### 1. Start kernels of non-opted-in topics without the proxy (main fix)

- **Remember the user's settings.** Before `engine.py:311` overwrites anything, store the original values of the 8 variables it sets, as JSON in a marker variable such as `CLM_HTTP_REPLAY_PREPROXY_ENV` (`null` means "was unset").
- **Docker.** `_mitmproxy_docker_env` sets the same marker with every value `null`. The container never had a proxy of its own, so removing them is correct there. The same applies to the `NO_PROXY`/`no_proxy` it adds.
- **New helper.** Add `kernel_env_for(tag) -> dict | None` in `notebook_processor.py`:
  - it returns `None` (inherit everything, as today) when the marker is absent (no proxy this build) or the notebook has a tag;
  - otherwise it returns `os.environ` with each of those variables set back to its original value, or removed if it was unset.
- **Wiring.** `TrackingExecutePreprocessor` gets a `kernel_env` attribute, set in `_execute_notebook_with_path`. Its `async_start_new_kernel(**kwargs)` override adds `env=self.kernel_env` when that isn't `None`. nbclient already forwards these arguments to `start_kernel`, so no other plumbing is needed.

The fix sits where the kernel is started, and the notebook processor runs in the same place as the kernel in both modes. So one change covers Direct and Docker, and the per-container env in `worker_executor.py` needs nothing per notebook, contrary to what the issue suggests. Non-opted-in decks get back exactly the network setup they had before the proxy existed, including a user's own corporate proxy.

### 2. Clearer warning (small, worth doing anyway)

After fix 1, an untagged request can only come from an opted-in kernel. Either a client library isn't tagged (e.g. `urllib.request`), or a subprocess such as `pip` or `curl` read the proxy variables. The text in `_warn_untagged_once` (`addon.py:601`) should name those causes and also cover a worker built with an older clm. It can't name the notebook, because the tag is the only thing that identifies it. The forensic trace (`CLM_HTTP_REPLAY_TRACE=1`) remains the way to find the notebook, and the warning should point to it.

### Why not option (b), tagging every kernel as "passthrough"?

- It still sends all traffic from non-opted-in decks through mitmproxy's TLS interception. Any tool with its own certificate store or its own way of reading proxy variables (git, HF hub, subprocesses) can then break, or still arrive untagged.
- The issue argues (b) keeps clients that ignore the proxy variables consistent. But those clients never reach the proxy anyway, so that argument doesn't hold.
- It needs a new tagging step in the injected code and a new path in the proxy add-on. Option (a) removes the problem instead of handling it.

## What changed

- **Kernels of topics without `http-replay` no longer use the replay proxy.** Before the build overrides the proxy settings, it records their previous values. Kernels of non-opted-in topics start with those values restored, so a user's own corporate proxy still works. This covers both Direct and Docker mode.
- **Opted-in topics always keep the proxy, even without a tag.** The review caught this one. In `replay` mode, an opted-in deck whose cassette is missing gets no tag. My first version would have let that deck call the real API with real keys; now strict replay still refuses it.
- **Docker:** the restored values are the proxy from `~/.docker/config.json`. Docker passes that proxy into every container by default, and the replay setup was overriding it.
- **The host environment is restored when the proxy stops.** Before, nothing cleaned it up, so a second build in the same process (MCP server, test session) inherited a dead proxy.
- **Clearer warning:** `CLM-HTTP-REPLAY-UNTAGGED` now lists the causes that are still possible: an HTTP client the bootstrap doesn't tag, a subprocess such as `pip` or `curl`, or an older Docker worker image.
- **Docs:** I updated the `spec-files` and `migration` info topics and the user guide, and added a changelog fragment.
- **Notebook output epoch bumped to 5.** Non-opted-in decks now run with a different kernel environment, and I couldn't argue their output can't change, so the project rule requires a bump. The next build re-executes every notebook once.
