## Agent

My opinion: **its own verb pair — `clm slides polish task/accept`** — and the decisive criterion is exactly the one you asked about. Discovery in CLM agents is name-first, domain-second, and only then docs:

1. **Name match is the first discovery path.** An agent told to "polish this deck" greps `clm info commands` or the `slides --help` tree for *polish*. Today that lands on the command immediately; converting it to a `DefaultVerbGroup` (report/task/accept/autopilot, exactly like `translate` just became in #961) keeps that hit and upgrades it. Under `harvest task --kind polish`, the capability is invisible at every name-matching layer: `harvest --help` says narration-from-recordings, nothing about prose levels. The agent must already *know* polish hides there — that's recall, not discovery.

2. **Prefix pruning works against the harvest home.** Agents (and humans) prune the command tree semantically: `harvest` = video narration, `slides` = deck authoring. Polish is deck prose. A semantically misfiled capability loses to one that's where you'd look, even with identical docs.

3. **`--kind` is already carrying two input shapes; polish adds a third.** I just confirmed the current surface: `polish FILE --lang de|en [--slides-range] [--level]`. Harvest's kinds switch between VIDEO-args (curate/translate) and `--source` file pairs (port/compare); polish would add level+range+lang on a single deck file. Conditional flag surfaces are where agents generate usage errors — usage errors are discovery friction.

4. **Info-topic routing.** The kit contract gives each toolkit an `<x>-agents` home. `slides polish` slots into the slides documentation family agents already read when authoring decks. Under harvest, every slides-side pointer has to cross-reference into `harvest-agents` — a domain jump mid-task.

5. **Pattern reuse compounds discoverability.** An agent that just learned the translate loop (`report → task → accept`) drives polish with zero new concepts if it's the same shape. A fifth `--kind` dialect branch is a new concept.

The steelman for `harvest task --kind polish` is real but weak on *discovery*: it's strongest if polish were a narration-quality step *inside* the harvest pipeline (curate → polish narration → accept), where loop context would dominate. And the code-layout argument (level prompts live as markdown files like harvest's prompts) is an internal concern — prompt files can be read from anywhere; the CLI surface is the contract.

One hybrid worth naming so it's explicitly rejected rather than implicit: keeping `slides polish` as the *only* surface while the framing internals reuse the harvest prompt-loading helpers — that's fine and orthogonal; it's about code, not surface.

## What's genuinely good (don't touch)

- **Top-level domain groups** make prefix pruning work (`slides` = deck authoring, `harvest` = narration from recordings, …) — the semantic filing agents and humans both use.
- **`harvest --help` is the best in-repo example** of surface-as-documentation: it teaches the agent loop, separates the diagnostic tier, and marks the autopilot quarantine. The kit contract (read-by-default, 0/1/2, envelope) is now consistent across sync/harvest/translate.
- **`clm info commands` is the real discovery index** for agents — version-accurate and canonical. `--help` trees are the secondary path; hidden aliases/diagnostics keep them clean.

## Non-orthogonalities worth acting on

1. **`coverage` vs `coverage-report` — and #963 makes it acute.** They're different things (bullet coverage vs DE/EN completeness) behind near-identical names. When #963 adds `coverage report` as a verb, you get a *literal* collision: `clm slides coverage report` ≠ `clm slides coverage-report`. The rename decision (or folding completeness into the `sync report` sweep) should be made *in* #963, before the verb lands — retrofitting a rename afterward costs a migration entry and downstream churn.
2. **The narration lifecycle is spread across three groups with no map.** Voiceover cells are touched by `harvest` (curate), `sync` (member reconciliation incl. companions), `voiceover extract/inline` (relocation), `slides coverage` (judgment), `slides reconcile-vo-ids` (id repair). Each placement is individually defensible — they're different lifecycle stages — but an agent only learns the boundaries by reading three info topics. One short "which command owns which narration stage" section in an existing topic would close that gap cheaply.
3. **Superseded stragglers.** `suggest-sync` is registered but hidden — if it predates the v3 `sync report` framing, it's a retirement candidate in the #960 no-shim tradition. (I haven't verified its current semantics — an investigation item, not a claim.)
4. **The remaining kit dialect**: sync says `apply --decisions`, harvest/translate say `accept --answer`. It's documented in `clm info agent-tasks` and semantically motivated (answers-to-items vs one task document) — I'd leave it, just noting it's the one place the "no third dialect" rule already bent.

## What I would *not* do

A big-bang regrouping of `slides` into subgroups. CLM has paid the alias-removal tax twice (1.6→1.8, then #310), the conversions are improving the surface faster than a reorg would, and `clm info commands` already carries the index role a reorg would try to serve.
