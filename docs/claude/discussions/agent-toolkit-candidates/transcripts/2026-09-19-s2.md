## What "agent toolkit" means in clm today

The sync and harvest designs share one contract, and any new conversion should reuse it rather than reinvent it:

- **Read by default.** The bare command reports; every write is an explicit verb.
- **Emit, don't invoke.** Judgement is framed as a JSON task with instructions, inputs, an answer schema, and freshness tokens the agent must echo back. The engine validates shape and freshness only, never quality.
- **Ledger as trust store**, stable member handles, load-bearing exit codes (0 clean / 1 work pending / 2 error).
- **An `<x>-agents` info topic** and a read-only MCP mirror. Writes stay CLI-only.
- **Embedded models survive only behind `autopilot`** for agent-less humans, never in CI.

## Candidates, ranked

**Tier 1: features that still invoke a model inside clm.** These are the direct analogues of the pre-pivot sync engine.

1. **Voiceover revision history: `harvest port`, `compare`, `compare-from-inventory`, `backfill`, `sync-at-rev`, `autopilot`.** All five run embedded LLM merge/port/compare prompts (`src/clm/voiceover/{merge,port,compare,autopilot}.py`). There is no `task`/`accept` equivalent for "carry old-revision bullets onto HEAD" or "label bullet relations". Converting them retires the largest embedded-LLM code in the repo and makes the whole transcription domain consistent. Related gap: the heuristic judgement points (OCR-to-slide matching, transcript-to-slide alignment, revision scoring) are engine-internal. An agent cannot see low-confidence assignments or override them except through the blunt `--transcript`/`--alignment` injection files. An `align report` listing uncertain segments as items would close that.
2. **`clm slides translate` (bootstrap).** Hard-stops without an API key and translates the whole deck itself. Its prompt seam is already shared with `sync task` (`src/clm/slides/sync_translate.py`), so `translate task DECK` emitting every lang-tagged cell plus glossary, and `translate accept` writing the twin, minting ids, and recording the ledger, is mostly plumbing. Today `--dry-run` only counts cells.
3. **`clm slides polish`.** Prose in, prose out, one chat completion, no JSON. The level prompts already live as markdown files, so this is the cheapest conversion. It may belong as `harvest task --kind polish` rather than a separate verb.
4. **`clm slides coverage` and `assign-ids --llm-suggest`.** Both call a local Ollama model for a single verdict or title. Coverage is a pure judgement with a cache; `coverage report` could emit bullet/voiceover pairs and `coverage accept` could bank verdicts. `assign-ids --json` already emits the refusal report; the missing piece is an accept side that takes agent-proposed titles for refused cells.
5. **`clm export summary` and `export context --level summary`.** LLM prose with a summary cache. Lower priority because `context --level full` already hands an agent the raw material. The useful addition is letting the cache accept agent-written summaries so `context` reuses them.

A side effect: the open TODO about one uniform per-purpose LLM model configuration mostly dissolves once these paths emit instead of invoke.

**Tier 2: deterministic features locked behind human output.** No model involved. The fix is structured output plus a report verb, not a redesign.

- **`clm recordings`.** `status`, `jobs *`, and `backends` are Rich-only. The per-course state JSON and the jobs ledger are good agent inputs already, and `drift --json` exists. The "which deck to record next" decision is a heuristic the agent-harness draft already names as judgement territory. Add `--json` to `status`/`jobs` and a `recordings report` combining drift, missing parts, and next candidates. The recordings dashboard has two JSON routes and no auth, so it is not an agent surface.
- **`clm calendar check/status/push`.** Plain-text diagnostics with exit codes. The TOML is hand-edited and clm never writes it, so an agent editing it needs `check --json` with structured findings and `push --dry-run --json` for the plan.
- **`clm release`.** Already ledger-driven, which is why you count it as agent-shaped. Gaps: only `channels` has `--json`. `status --json` and `sync --dry-run --json` would let an agent decide what to release without parsing tables.

**Tier 3: stays CLI-first, gains affordances.**

- **`clm build`.** `--output-mode json` already emits a rich envelope (errors with actionable guidance, rebuild reasons, flaky files). It goes to stdout only. A `--report FILE` that persists it would let agents inspect a build after the fact. `kernel-triage` already scrapes this JSON, which shows the demand.
- **`clm git`.** `status --json` across `--all` would answer "is any cohort repo behind" in one call.

**Not worth converting:** `validate`, `course gate/orphans/renumber`, `cache explain`, `cassette`, `kernel-triage`, `query`, `export outline` (all JSON-capable already), and the infrastructure groups (`workers`, `jobs`, `db`, `docker`, `provision`, `monitor`, `jupyterlite`, `zip`).

**Cross-cutting recommendation.** Extract the task/accept contract that harvest and sync each implemented separately (answer envelope, freshness tokens, member handles, validator registry) into one shared module before starting Tier 1, so polish, translate, and coverage do not produce a third dialect. Each conversion also needs its own `clm info <x>-agents` topic.
