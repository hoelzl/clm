The smallest repro uses the PR's own `TestIdReorderPlusPoolReorder` fixture. EN becomes `[c2 = 20][vo B][vo A][c1]` (or `[c2 = 20][c1][vo B][vo A]`).

- **After the PR:** pass 1 suspends the slot and only the scope mirror lands. Pass 2 asks a `pool_placement_divergence` question on a cell that is still edited. Answering `en` moves DE's cell but keeps DE's old content. The pre-write verify sees a new `[unify]` mismatch and withholds the row, and the same row comes back every pass with nothing left to answer.

That is the exact failure class #1124 was filed for. The PR says "on the next pass the edit propagates and the placement frames". That only holds when pass 2 has no placement question for the edited slot, which is true of the filed shape but not in general.

**2. Medium: the cause is older than this PR, and #1124 and #1128 are both instances of it.**

The pre-merge code already livelocks on `[c1 = 10][x][vo A][vo B][c2]`: one cell moved across a voiceover and edited, with no id'd reorder. The cause is that the `en` answer to a placement question moves the other half's cell without taking the chosen half's content. The verify then rejects that state forever. #1128's write-up describes the same mechanism ("Answering `en` moves DE's `c2 = 2` without taking EN's bytes") but treats it as specific to the both-cells-edited case.

In the 4-cell run, 49 of the 60 cases that still livelock end on a `pool_placement_divergence` row. The PR fixes this downstream by changing which rows get raised, so the same dead end is just reached by other shapes. Making a placement answer carry the chosen half's content, or raising placement and edit as one question, would likely fix #1124, #1128 and this regression together. That is a design call.

## The root cause

The engine splits one logical change, "this cell moved *and* was edited", into separate rows. Since #1051 B2, the pre-write verify withholds any change that would *introduce* a violation. Each row is applied alone, and neither is valid alone:

- **A placement answer** (`mirror_pool_placement`) moves the cell but, by design, "the target cell keeps its bytes" (`src/clm/slides/doc_apply.py:1374`). After the move, the edit's divergence shows up as a `[unify]` mismatch between different cells. The `unify` check aligns cells by position, so the mismatch has new bytes in its locus and counts as "introduced". It is withheld every pass.
- **A propagated edit** applied beside the scope mirror, while the cell still straddles a voiceover, produces a mis-paired layout. That is #1124's pass 1.

Before B2, the intermediate state was written to disk and the next pass sorted it out. B2 made each row's projected result individually verify-clean, so any decomposition that is only valid *jointly* now livelocks. #1124, #1128, my regression shapes and the older move-plus-edit dead end all fit this one pattern. That's why fixing one shape by reshaping which rows appear just moves the dead end.

## Candidate fixes, to prototype before deciding

1. **Judge `unify` by slot, not by position.** Have the pre-write verify identify a `unify` mismatch by the paired slot, using the same pairing the differ uses, instead of by aligning lines. A divergence that only *moved* with its cell would then count as pre-existing, so the placement answer lands and the edit propagates next pass. This matches B2's stated intent: "a fault that merely moved keeps its identity." It's the narrowest change and probably fixes the regression and the plain move-plus-edit case. It probably doesn't fix #1124's pass 1, where the layout really is wrong.
2. **Make the answer total.** A placement question on a slot whose content also differs should carry the content too, so one answer settles position *and* bytes atomically. `conflict_shared`'s `de`/`en` answer already overwrites content this way. The hard part is the DE-edit case: there the right result is EN's position with DE's bytes, and the pairing may be a guess. So the question must show both bodies and let the agent decide the content. Copying bytes mechanically over a guessed pairing could lose an edit without the verify noticing. That's a vocabulary decision for you.
3. **Apply a slot's rows together.** Treat all rows on one slot as a unit that lands or is withheld as a whole, with the differ always emitting the content row next to a placement row. This is more general, but it touches the deferral rule and the per-group withholding in apply.

My guess: option 1 handles most cases with little risk, and option 2 handles the both-sides-edited cases, which need a human decision anyway. #1124 may still need a differ-side suspension, but a narrower one than #1129's. That's a hypothesis until it's measured.

## Agent


Step 3 comes down to one question: **should shared cells (code, un-id'd markdown) carry a stable identity, and if so, where should it live?** The design doc currently says no. Changing that is your call, not an engine detail.

## Why the question exists

Design doc §3.4 deliberately leaves shared cells without ids. Localized cells and narratives get a `slide_id`; shared code cells are identified by position within their span, plus a ledger fingerprint. The reasoning there:
- **Churn:** stamping would add roughly 11–13k ids across the courses.
- **Shared cells need byte-parity, not names.**

That position was challenged once already. A proposed opt-in mode where a whole deck carries ids (Q1 in §13) was **withdrawn on measurement**, with the rule "re-open only if a framed dead end recurs in the field".

The residual from #1144 is exactly the case that rule doesn't cover. When both halves move *and* edit the same slide's code cells between syncs, a fingerprint can't prove which edited cell is which. As you said, no positional rule fixes that reliably. Only something that survives an edit can tell the cells apart.

## The options

1. **Stamp every shared cell.** This reverses §3.4. It's a one-time `normalize --stamp-ids` commit per course repo, about 11k ids.
   - *Pro:* it closes the class completely, with one rule everywhere.
   - *Con:* every new code cell needs an id, so authors and agents must add one or re-run normalize. A copy-pasted cell duplicates its id, which sync refuses (`duplicate_id`). And most of those ids protect pools that never had a problem.
2. **Stamp only where position is ambiguous:** shared cells in a span that holds two or more of them. Q1's measurement says this targets where the risk actually is. Pools of 1–3 cells carry under 5% of the churn, and a few large pools carry most of it.
   - *Pro:* far fewer ids, aimed at the risk.
   - *Con:* the rule moves with the content. Adding a second code cell to a span makes the first one need an id. The engine's precondition check would then frame a "run normalize" item for it. Either the author runs normalize again, or `apply` mints the id. Minting from `apply` was rejected in #892 (no "mint_id" rows in the report), because it pulls normalization back into the sync loop.
3. **Keep identity out of the files; store cell bodies in the ledger.** Pairing could then match an edited cell to its most similar recorded body.
   - *Pro:* no file churn.
   - *Con:* it's still a heuristic. Two similar small cells (`c1 = 1` and `c2 = 1`) are where it fails, and it would fail silently. That's the whack-a-mole you rejected. The ledger also grows.
4. **Do nothing more.** Keep the residual, which is documented. Sync already tells the author to add a `slide_id` by hand where it sees the ambiguity, though sometimes the residual passes silently.

## My recommendation

**Measure before choosing.** Every case in the residual comes from the synthetic probe, not from real use. Q1's own rule asks for field evidence before reopening §3.4. Both halves moving and editing the same slide's code between two syncs may be rare in practice, because translators usually work on one half.

A scan of the course repos' git history (PythonCourses, CppCourses) for commits where both halves changed a slide's code cells, and their order, between two ledger records would tell us. It's a script and an afternoon.

- **If it shows up:** option 2 is the best trade.
- **If it doesn't:** option 4 stands, and §3.4 stays as it is.

Option 1 is the safest in theory but costs authoring friction everywhere. Option 3 just moves the guessing.

There are two decisions here:
1. Do you want the history scan first?
2. If you want to decide now: which option? If it's option 1 or 2, the open sub-question is who mints ids for new cells (normalize only, or apply too, which would reopen #892's rejection).
