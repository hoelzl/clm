## 1. Intermittent "Timeout waiting for notebook workers to activate"

**Cause:** clm waits a fixed 30 s for the Docker notebook workers to come up. Docker Desktop sometimes takes longer than that. When it does, clm marks all 8 workers as dead even though their containers are running fine, and a worker marked dead is refused when it finally checks in.

In your failed run (23:56):

| Time | Event |
|---|---|
| 23:56:29 – 23:57:07 | All 8 notebook containers start normally |
| 23:57:09 | First notebook job; the 30 s wait begins (`WORKER_ACTIVATION_TIMEOUT_SECONDS`, `sqlite_backend.py:65`) |
| 23:57:32 | PlantUML worker checks in after 25 s (normally 2–3 s) |
| 23:57:40 | Timeout. All 8 notebook workers marked dead and the build aborts |
| 23:57:42 | Draw.io worker checks in, 2 s too late for the notebook workers |

So everything in Docker was slow during that window. Your other runs that night had less margin than they appeared to: the notebook workers took 37–44 s from container start to checking in. They only passed because the 30 s count starts after all containers are running.

I reproduced this with a standalone 8+1+1 Docker pool:
- Normally a worker is ready 8–11 s after its container starts. Importing clm inside the container takes only about 2.5 s; Docker Desktop's container startup is the slow part.
- In one run, all 8 notebook containers sat frozen and then wrote their first log line at exactly the same moment (45.88 s), even though they had started between 16 s and 37 s. That is the same "all activate in the same second" pattern in your logs.

This freezing comes from Docker Desktop/WSL2 itself and varies without limit. I couldn't pin down what made it especially bad at 23:56.

Suggested fix:
- For Docker workers, don't declare a worker dead while its container is still running. Wait longer (around 120–180 s), and give up early only if the container has exited.
- Make the error message point to `docker logs <container>`. It currently names the local worker-log folder and `clm[all-workers]`, which don't apply in Docker mode.

**Workaround for now:** fewer notebook workers helps. Your two later builds with 4 workers succeeded. Simply re-running also usually works.

## 2. Speaker/Recording HTML is never reused from the cache

**Cause:** in Docker mode, the saved results are filed under one path and looked up under another, so the lookup always misses.

- The Docker worker saves each executed notebook under its container path, `/source/slides/…`.
- Before submitting a Recording/Speaker HTML job, the host checks for a saved result (`_can_replay_from_cache`, `sqlite_backend.py:801`). It looks under the Windows path, `~\…\slides\…`.
- The paths never match, so every build logs *"Recording HTML execution cache is cold"* (448–672 times per log file) and re-executes every deck. There is no cache indicator because nothing is actually reused.

`CppCourses/clm_cache.db` confirms this. For `slides_welcome_beginner`, the 2026-09-22 rows (from a Direct-mode build) are keyed `C:\Users\…`, and the rows written tonight are keyed `/source/slides/…`.

It started when the C++ course switched to `--workers=docker`. The mismatch has existed since the check was added (commit 6f510e41) but only shows up in Docker mode. The later HTML passes in the same build still reuse the saved results, because the Docker worker both saves and looks up under `/source`. Only the Speaker/Recording pass pays the full execution cost.

Suggested fix: save the executed notebook under the host's input path (the worker already has it as `job.input_file`), so both sides use the same key. The existing `/source/…` rows are harmless and would cost one more full build.

**Root causes:**
1. **faster-whisper and PyAV 19 are incompatible.** When faster-whisper 1.2.1 is given a file path, it decodes it with `av.open(..., metadata_errors="ignore")`, and PyAV 19 removed that keyword. faster-whisper only requires `av>=11`, and 1.2.1 is still its latest release, so there's no upstream fix.
2. **Tool installs don't use the lock file.** clm's `uv.lock` pins PyAV 17, so CI and `uv sync` were fine. `uv tool install` ignores the lock and picks up PyAV 19.0.1.
3. **The workaround couldn't help.** Transcription runs in a separate Python process (`python -m clm.voiceover._transcribe_worker`), which isolates crashes during CUDA shutdown. A patch applied in the parent `clm` process never reaches that child.

The PyAV decode was redundant anyway. clm already uses ffmpeg to turn the video into a 16 kHz mono WAV, and faster-whisper then decoded that same WAV a second time with PyAV.

**Fix:** clm now decodes the audio itself and hands faster-whisper the samples instead of a path. faster-whisper then never calls PyAV.
- The WAV that clm extracts is read directly with Python's built-in `wave` module.
- Anything else (other sample rates, stereo, MP3) goes through ffmpeg, which clm already requires.
- Every ASR path goes through this one place: `harvest`, `cached_transcribe`, the voiceover CLI, the MCP tools and the subprocess worker.
- I didn't add an `av<19` cap. clm no longer calls PyAV, faster-whisper still imports PyAV 19 fine, and a cap would only block PyAV updates.
