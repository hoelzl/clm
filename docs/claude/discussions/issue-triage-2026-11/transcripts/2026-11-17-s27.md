I've finished reading the code for #1288. The issue as I wrote it needs one correction, and there are a few decisions for you before I implement.

## Correction to the issue
- **The "~170 subdirs" figure is wrong.** CppCourses lists 18 subdirs under `code/completed` and 8 under `code/starter_kits` (45 and 34 exist on disk).
- **They're projects, not topics.** One project can serve several topics: `simple_examples` is referenced from at least 4 topic directories, `error_handling` and `test_examples` from 2 each. So a project can't map one-to-one onto a topic.
- **Good news:** `code/completed/CMakeLists.txt` and `code/starter_kits/CMakeLists.txt` already wrap `add_subdirectory` in `if (IS_DIRECTORY …)`. So a channel that hasn't received a project yet still configures. I'd document this as a requirement for any course using per-topic code.

## Proposed implementation
- `<subdir topic="…">` on a global dir-group. An optional `<dir-group topic="…">` sets an owner for the whole group, and a `topic` on a subdir overrides it.
- Each owned subdir is recorded in the manifest with its topic and section, exactly like a topic-scoped dir-group.
- Root files (`include-root-files`) and subdirs without an owner stay skeleton.
- Release sync and adopt need no changes, because they already group files by `topic_id`.

## Decisions (my recommendation in bold)
1. **A project used by several topics:** **one owner, the earliest topic that uses it**, so the project ships with that topic. Later changes to the project for later topics reach students only through `--refreeze` of the owning topic. The alternative, several owners per file, would break the manifest's one-topic-per-file model and the freeze bookkeeping, so I advise against it.
2. **The owner topic is in a disabled section:** **don't copy the subdir**, which is the existing rule for topic-scoped dir-groups and avoids a leak. The catch: disabling a section also removes a shared project owned by one of its topics. `clm validate` would print a warning naming the subdir.
3. **Unknown topic id:** **a spec error**, in both `clm validate` and `clm build`.
4. **Channels that are already frozen, like CppCourses after adopt:** **no special handling, just documented.**
   - Files now owned by a frozen topic keep the version students have; only a `--refreeze` of that topic changes them.
   - Files owned by a topic not yet released ship when it is released, overwriting any copy already present.
   - Caveat: refreezing a topic now also re-copies its starter kit. That changes students' files only if the starter kit itself changed.
5. **CppCourses annotation:** **own `completed` and `starter_kits`, and leave `external`, `.devcontainer`, the root files and `div/toplevel/common` as skeleton.** I'd do it as a CppCourses PR right after the clm PR. The owner for each project comes from where the slides reference it, and you review the mapping. It has no effect on students until the deferred refreeze, because every topic is already adopted.

I'll post the correction and these decisions on #1288 once you've answered. Shall I go with all five as recommended?

## What exists

- **The recordings workflow already has a fixed layout.** The dashboard computes it from the spec's `Course` object:
  - `final/<course output name[lang]>/<section name[lang]>/<deck file name>[ (part N)|(Teil N)].<ext>`
  - `naming.final_filename` builds these names and `naming.parse_part` reads them back; both handle `part` and `Teil`.
  - So the batch can find exactly the files the workflow wrote, from the spec and without any file-name pattern.
- **No checked-in record holds the video paths.**
  - The recordings ledger in each topic (`.clm/recordings-ledger.json`) stores parts, course and language, but no file names.
  - The per-course state file holds `processed_file` and `topic_id`, but it lives in this machine's config directory and only covers takes recorded through the dashboard.
- **Part numbers can legitimately have gaps.** `invalidate` never renumbers the remaining parts.
- **The sync ledger already records which videos were harvested.** `accept --record` stores the provenance `harvest:<video_fingerprint>`, where the fingerprint is the path, modification time and size of the ordered parts.
- **The `report` and `task` commands require a deck path** as their first argument today.

## Decisions

**D1. Where the videos come from.**
- **Recommended: compute the layout from the spec, as the dashboard does.** `--recordings-root` defaults to `recordings.root_dir`.
- Rejected: the state file, because it exists only on one machine and misses videos recorded outside the dashboard.
- Rejected: patterns over the directory tree, which caused the bug in the first place.
- Videos stored outside the layout keep the current per-deck form with explicit paths.

**D2. The shape of the commands.**
- **Recommended: no new command.** `report`, `task`, `accept` and `verify` gain `--spec` addressing, and the deck path becomes optional: give exactly one of a deck path or `--spec`.
- **Only `report` runs as a batch over the course.** `task`, `accept` and `verify` stay single-deck, addressed with `--spec X --topic T` plus `--deck STEM` when a topic holds several decks; anything ambiguous is refused.
- Each deck in the batch report carries the exact follow-up `task` command for its actionable slides, so an agent never builds a path.

**D3. How decks are addressed.**
- **Recommended: `--topic` is an exact topic id**, resolved through the spec as `clm course decks` does: never a suffix or a pattern. That alone fixes `strings` matching `c_strings`.
- **`--section` takes a section id, or the section's 1-based position** where sections have no id, as in cpp-for-programmers.

**D4. Multi-part videos.**
- **Recommended: order the parts by part number.** A gap is a note, not an error, because invalidation leaves gaps.
- **When an unnumbered file and numbered parts both exist, that deck reports an error.**
- **A deck with no video is listed as `no_recording`.**

**D5. Output and exit codes of the batch.**
- **Recommended: one JSON envelope** with an entry per deck: its topic, section and videos, a status of `actionable`, `nothing`, `no_recording` or `error`, and either the deck's ordinary report or the error. A summary goes on top.
- **One deck failing doesn't stop the batch.** An example failure is a deck that isn't normalized.
- **Exit codes:**
  - 0 when nothing is left to harvest;
  - 1 when at least one deck is actionable;
  - 2 for a spec or usage error, or when any deck failed. An error outranks "actionable" so that an agent can't miss it.

**D6. A cheap check of the mapping first.**
- **Recommended: a `--resolve-only` flag** that prints only the deck-to-videos mapping, without transcription.
- A full batch over 37 videos means GPU minutes per video, so seeing the mapping first is worth it. It is also the natural thing to put in agents' instructions.

**D7. Harvesting only what's new (the issue's optional item).**
- **Recommended: `--unharvested`.** It skips a deck when its current video fingerprint already appears as `harvest:<fp>` in the deck's sync ledger.
- That's more accurate than `--since <date>`, which would depend on file modification times.
- One limitation: moving the files changes the fingerprint, so those decks count as unharvested again. That errs on the safe side.

**D8. Documentation.**
- **Recommended:** rewrite the loop in `clm info harvest-agents` around spec addressing, update `clm info commands`, and add a changelog fragment.
