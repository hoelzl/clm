## The rule I'd use

Every time the worker renders a diagram:

1. Render once and compare the bytes with the PNG already at the output path (the `img-generated/` file tracked in git).
2. If they match, accept it. That costs one render.
3. If not, render a second time. If the two new renders match each other, accept and cache.
4. If they still disagree, try a third time. If there is still no agreement, fail the job loudly: cache nothing and leave the existing file alone.

This is your idea without the "is the source unchanged?" branch. The worker doesn't need to know why it's rendering; the comparison sorts it out:

- **Source unchanged** (drive move, cache wipe, new image version): the render almost always matches the stored file, so it costs one render. That covers nearly all mass re-renders, which is where the risk is.
- **Source edited:** the first render won't match, so it costs two. That only happens for the few diagrams someone actually changed.
- **New converter version that draws slightly differently:** the first render won't match, but two new ones will. It costs two renders once, then things settle.

Leaving out the branch also avoids a trap. "Source unchanged" would have to be judged by the cache, and a cache entry that's broken is exactly the case we're guarding against.

## Why it fixes this incident

- **It repairs itself.** In this incident, the file in `img-generated/` was itself the broken image. With this rule, a good render won't match it, the second render will match the first, and the good image wins. A bad file in git can't lock in a bad result.
- **Exports are deterministic when they work.** That's the premise, and we checked it: six renders across 1.34.3 and 1.39.0 were byte-identical.
- **One limit:** this protects only new renders. A broken entry that's already in the cache is reused without rendering, so it bypasses the check entirely. That's why option 4 (`clm cache forget <file>`) is still needed.

## Why I'd skip the settle delay for now

- It only helps if missing paint is really the cause. That's my guess from the tile pattern, not something we've confirmed.
- It costs time on every render, and most of all in a mass re-render, which is exactly the slow case.
- With the comparison in place, a partial render already gets caught and redone.
- Better: log every mismatch and retry. If the logs show this happening often, fix the cause, probably by running fewer draw.io instances at once rather than adding a fixed wait.

## One thing I'd add

The trigger was a re-render that shouldn't have happened at all. The cache is keyed by absolute path, so moving the repo to `G:\` re-rendered every diagram, even though old rows with identical content were already in the database. clm has a cache path migration feature (it came up in #587); running it before builds on the new drive would have avoided the whole burst. A lookup by content hash as a fallback would make this automatic. That's worth a separate small issue.

If the host writes the files instead, the host has to send the old image's hash along with the job. I'd confirm that in the clm source first.

**`clm cache forget PATH... [--dry-run] [--json]`**
- Give it a diagram, a slide deck, or a generated output file, and it deletes every cached version of it from both cache databases. No `--spec` is needed.
- For a source file it also finds the outputs that file produced, from the stored results, and clears their job-cache entries. Without that, the next build would still skip the render, because the broken image on disk matches its own cached entry.
- Path matching ignores case and slash direction on Windows.

**Checking each render before it is cached** (PNG only)
- **Matches the image already on disk:** accepted after one render. This is the usual case when an unchanged diagram is re-rendered.
- **Doesn't match:** rendered again and accepted if the two renders agree. That covers edited diagrams, new converter versions, and a broken image on disk, which then gets replaced.
- **Three different renders:** the job fails, and the existing image and the cache are left alone. Every mismatch is logged as a warning.
- PDF is excluded because it embeds a timestamp, so two good exports never match byte for byte.
