## How the editor side maps to VS Code

| JupyterLab spike | VS Code equivalent |
|---|---|
| CodeMirror transactions without a user-event tag (no auto-indent, no bracket auto-close) | `TextEditor.edit()` on the cell's editor. Auto-close, Enter indentation and format-on-type only run on real typing, never on edits made by code, so this is the same guarantee you get in JupyterLab. |
| Showing a selection before deleting it | `editor.selection = new Selection(...)` |
| Hacker mode: a capturing `keydown` listener that swallows keys | Override the built-in `type` command while a cell is armed, and dispose the override on disarm. The VSCodeVim extension and the "hacker-typer" extension both use this. |
| Keys that don't go through `type` (Backspace, Delete, Tab, Enter) | Keybindings under a `clmTyping.armed` context key that do nothing while armed |
| Shift/Ctrl/Alt+Enter disarm, then run | Armed-only keybindings that disarm and then call the normal cell-run command |
| Settings (`mode`, `charsPerSecond`, `jitter`, …) | VS Code settings with the same names, plus a toggle-mode command |

## Risks to check in a spike

1. **`type` conflicts with VSCodeVim.** Only one extension can own `type` at a time. Taking it only while a cell is armed limits the conflict, but it should be tested with Vim installed, or the recording profile should leave Vim out.
2. **Copilot ghost text.** Inline completions fire on any document change, including edits made by code, so grey suggestions could show up on video. The fix is to turn Copilot and inline suggestions off in a dedicated recording profile, not in code.
3. **Edits are asynchronous.** Each `edit()` is a round trip to the editor process. That's fine at 22 characters per second, but fast key presses in hacker mode need a queue that runs one edit at a time. The JupyterLab player is synchronous and can't be dropped in as-is.
4. **A cell needs an open editor.** Showing a selection only works on a cell that is in edit mode. The player should put the cell into edit mode before it starts.

I recommend a separate extension, kept in the `jupyterlab-clm-typing` repo as a `vscode/` package that imports the shared `planner.ts`/`player.ts` and is bundled with esbuild:

## Agent


Mostly no. The only cost you'd notice is that while a cell is armed, single-key notebook shortcuts stop working until you disarm.

**How it would work:** extra keybindings that are only active while a cell is armed and the notebook is in command mode. They would cover the printable keys, Space, Enter and Backspace. Pressing one would put the armed cell back into edit mode and type the next few script characters, as in edit mode. VS Code doesn't tell an extension when a cell drops into command mode, so this is the only reliable way to catch it.

**Consequences:**

1. **Notebook shortcuts are blocked while armed.** `A`, `B`, `M`, `Y`, `D D`, `Z` and the other single-key commands would type the script instead. If you clicked into command mode on purpose to insert a cell, you'd have to disarm first (Esc or Alt+N). That matches what "armed" already means: the keyboard belongs to the script.
2. **Keys with Ctrl, Alt or Cmd pass through untouched.** Shift+Enter, Ctrl+Enter, Ctrl+S, Alt+N and slide-nav's Ctrl+Shift keys keep working, and Shift+Enter still runs the cell and disarms.
3. **Keyboard layout.** On a German layout, binding by character could miss `ö`, `ä`, `ü`, `ß` or the `y`/`z` swap. Binding by physical key position (`[KeyA]`, `[Digit1]`, `[BracketLeft]` …) covers every key on any layout, so I'd do that. Any key that still slipped through would just behave as it does today.
4. **Shortcut list clutter.** This adds roughly 60 entries to the Keyboard Shortcuts editor. They have no effect while nothing is armed.
5. **A small timing gap.** If you click another cell's margin and press a key within a few milliseconds, the extension may not have disarmed yet. The handler would check whether the armed cell is still selected; if not, it disarms. The key would be dropped, not run as a notebook command. That's a lost keystroke, not an unexpected new cell.
6. **A stuck flag after a crash.** If the extension crashed while armed, the "armed" flag could stay on, and command-mode letters would go to a dead command until you reload the window. Clearing the flag at startup covers restarts, so this would only happen in a real crash mid-recording.
7. **A short pause on the first key.** Getting back into edit mode takes a round trip of a few tens of milliseconds. Later keys are already in edit mode.

There's also a more conservative variant: in command mode, any key just disarms and is dropped, with no typing. It's safer, but it gives the half-armed situation a different symptom instead of removing it. I'd go with re-entering and typing, since that matches how hacker mode already feels.
